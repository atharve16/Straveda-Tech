# Authentication and user management source audit

Source reviewed: `02-web-portal-source/auth.php`, `outlet-users.php`, `users-store.php`, `regions.php`, `config.example.php`, the related calls in `orders.php`, `api.php`, `index.html`, `orders.js`, `03-demo-data/users.demo.php`, `03-demo-data/schema.sql`, and the demo JSON/SQLite seed. This report describes the supplied PHP, not the missing live installation. No Android authentication code was written.

## Route-wide contract and an important method distinction

`auth.php:7-31` includes configuration/storage/mapping code, starts a PHP session, creates a 32-byte random CSRF token if absent, sends JSON and no-cache headers, decodes a JSON body (or uses `[]` when JSON is `null`), and chooses `$_GET['action']` before `$body['action']`. It does not require a non-null decoded JSON value to be an array, so scalar JSON has no controlled validation contract. The router has **no global HTTP method check**. It calls `usersLock()` only for POST actions other than `login`, `logout`, and `check`. It does **not** perform global CSRF verification. Only the six outlet-profile routes call `outletActor()`, which requires a body `csrf` even for a GET request. Thus the browser's normal GET reads and POST writes are conventions; JSON-body mutations through GET are reachable and have no file lock for officer actions. A plain GET without a JSON body cannot supply the needed mutation fields. All errors emitted with `echo` alone retain HTTP 200; `actor()`/`denyJson()` emit HTTP 403, `usersLoad()`/`usersWriteFail()` emit 500. The `auth.php` default is HTTP 400 `{"ok":false,"error":"Unknown action."}`. Source: `auth.php:18-31,745-747,995-1008`, `users-store.php:46-94`.

For the action entries below, **method `*`** means PHP accepts any method with JSON body fields; the frontend's actual method is stated separately. **Lock P** means POST acquires the best-effort `users.lock` before dispatch; GET does not. There is no SQLite/MySQL transaction unless explicitly stated. Officer file writes go through `writeUsers()` → `usersWrite()`; this is an atomic-temp-file attempt with a direct locked-write fallback, not a database transaction. All listed officer actions read `users.php` through `usersLoad()` unless stated otherwise. Android migration requirements are logical contracts only; no service is implemented.

Frontend call topology was checked against the PHP switches. `index.html:1093-1120` sends login tab and credentials, `1238` sends logout, `2376-2610` uses the older direct account-management fetches, `3540` changes a password, and `3606` checks the session. `orders.js:98-100` constructs `auth.php?action=<action>` for reads and JSON `{...data,action,csrf}` for POSTs; its call sites at `877,2105,2253-2433,2450-3034,3765-3832` cover contact, sales-area, outlet, officer, super-admin and import routes. This dynamic helper is why searching only for literal `auth.php?action=...` would miss most actions. The ordinary browser pattern is GET for `check/list_users/list_sales_areas` and POST for the other actions; PHP itself does not enforce that split. No extra authentication action name was found in the supplied frontend beyond the 23 router cases. `orders.php` includes `outlet-users.php` for downstream order scope and `api.php` includes the same officer store; neither adds an `auth.php` route.

## Individual action contracts

### 1. `login` — `auth.php:33-139`

Method `*`; frontend POST at `index.html:1120`; body `username`, `password` required after `trim`, `org` optional (browser sends `rohan`, `hpcl`, or `sap`); no query field beyond `action`, no CSRF guard, no initial file lock. Empty credentials → HTTP 400. `org=sap`: `ouFind()` reads `portal_outlet_users` left-joined to `portal_outlets`, validates 6–12 SAP digits, then `password_verify`; database error → 500, invalid credentials → 401, missing zone or region → 403. It creates `ouSession()`, regenerates session ID and returns `{"ok":true,"user":…, "csrf":…}`. Other tabs: `usersLoad()` reads `users.php`; an exact username wins, otherwise a single case-insensitive match is accepted; zero or multiple matches fail 401. An unknown officer username is checked via `ouIsProfile()` to append a SAP-tab hint. `$2y$` passwords use `password_verify`; non-`$2y$` values use strict plaintext equality. On successful legacy plaintext verification the route takes `usersLock()`, reloads, and conditionally hashes/writes the old password **before** the organization-tab check. A later tab mismatch can therefore return 401 after that write. `org=rohan|hpcl` must match a nonempty stored `org`; a null/empty `org` works under either tab. Any other/omitted `org` does not enforce the tab match. Officer success uses `userLevel()` and the current stored account to build the session. Android: retain separate officer/outlet lookups, tab checks, conditional legacy migration and local session refresh; do not copy the PHP server interaction.

### 2. `check` — `auth.php:140-170`

Method `*`; frontend GET at `index.html:3606`; no required body/query field except selector, no CSRF guard or file lock. An outlet-flag session calls `ouFind(ouDb(), username)` and `ouSession()` again; a deleted profile, missing zone/region, or caught database failure destroys the session and returns HTTP 200 `{"ok":false}`. It refreshes label, zone, region, sales areas and all outlet identity fields. An officer session reloads `users.php`; a missing username destroys the session. It refreshes only `hidden_cols`, `hidden_pages`, `org`, `ros`, `level`, `sales_areas`; it **does not** refresh `role`, `label`, `filter`, or `username` in the session. Guest returns `{"ok":false}`. Valid sessions return `{"ok":true,"user":…, "csrf":…}`. No application SQL write or transaction. Android: re-read identity on resume/launch and explicitly decide how to handle the PHP's partial officer refresh; do not assume it revalidates every cached field.

### 3. `logout` — `auth.php:171-175`

Method `*`; browser POST at `index.html:1238`; selector only, no auth/CSRF/lock. Calls `session_destroy()`, no application table or file change, no transaction, HTTP 200 `{"ok":true}` even for a guest; no action-specific error branch. This reconfirms the earlier `AUDITED` contract. Android: clear local identity/session and cached authorization state.

### 4. `list_users` — `auth.php:176-212`

Method `*`; browser GET (`index.html:2376`, `orders.js:2450`); selector only, lock P, no CSRF. `actor($users,'any')` permits a super admin or Zone Officer; 403 otherwise. Rohan super admin sees all accounts; HPCL super admin sees HPCL `role=zone` accounts (because `canManage()` and `superLimit()`), and a Zone Officer sees Regional Officers whose `created_by` equals that actor. `canViewPassword()` separately excludes self and super-admin targets. The response is HTTP 200 `{"ok":true,"users":{username:{label,role,filter,hidden_cols,hidden_pages,org,ros,sheet_zone,states,sheet_zones,zones,level,created_by,sales_areas,email,mobile,can_see_pw,password,pass_by,pass_at}}}`. `password` is a decrypted readable copy or empty; the bcrypt hash is never sent. Reads `users.php`, mapping constants, and possibly decrypts `pass_view`; no SQL/application write. Android: enforce row-level listing and password-view policy in the local service, independent of page visibility.

### 5. `list_sales_areas` — `auth.php:213-225`

Method `*`; browser GET (`orders.js:2105`); selector only, lock P, no CSRF. `actor(...,'any')` permits super admins and Zone Officers. A super admin iterates all sheet zones; `superLimit()` currently returns `null`, so no regional restriction is applied. Zone Officers use `officerRegions()`. Returns HTTP 200 `{"ok":true,"sales_areas":{region:[sales-area,…]}}`; reads `users.php` and `regions.php`, no SQL/application write. Android: use a bundled version of the mapping and reproduce current scope.

### 6. `update_user_access` — `auth.php:226-351`

Method `*`; browser POST (`index.html:2476,2535`, `orders.js:3809`); lock P, no CSRF. `actor(...,'super')`; HPCL super admin additionally requires `canManage(target)`, new `role=zone`, and any supplied `org=hpcl`. Body requires trimmed `username`, `role`; optional `filter`, `label`, `sheet_zone`/`sheet_zones`, `ros`, `org`, `hidden_cols`, `hidden_pages`, `email`, `mobile`, `new_username`. Roles allowed: `superadmin|cluster|zone|state|ro|entry`. `cleanZones()` validates selected sheet zones and optional regions; `validateOrg()` checks officer organization/zone; `applyPages()` ignores a self-target. A continuing super admin or Regional Officer only has label, column visibility and page visibility changed by this route; other requested changes are ignored. For other targets, child Regional Officers block role/org removal or loss of any covered child region; org changes propagate to children. Contact changes use `cleanContact()`; rename uses `renameUser()` and dynamically updates every current MySQL table with a username-like column, then changes officer-file keys, child `created_by` and `pass_by`. Other success writes `users.php` and returns `{"ok":true}`. Validation/not-found/child errors return HTTP 200 `{ok:false,error}`; actor denial 403; storage error 500. **Non-atomic boundary:** `renameUser()` commits SQL before `usersWrite()`, so a later file-save failure can leave database and officer file out of step. Android: use one local transaction for account/reference rename and preserve the observed restrictions; treat ignored fields deliberately.

### 7. `update_user_password` — `auth.php:352-378`

Method `*`; browser POST (`index.html:2482`, `orders.js:3826`); lock P, no CSRF. `actor(...,'any')`, then `canManage()` target; own target is not explicitly excluded for a Rohan super admin. Body `username`, `password` required after trim, password minimum 8 bytes (`strlen`). Missing/not-manageable target reports HTTP 200 `User not found.`; invalid input/short password also HTTP 200. `setPassword()` writes bcrypt hash, optional encrypted `pass_view` (never for super admins), `pass_by`, `pass_at`; `writeUsers()` persists `users.php`; success `{ok:true}`. No SQL transaction. Android: preserve viewer rules and metadata; do not expose hashes.

### 8. `change_password` — `auth.php:379-414`

Method `*`; browser POST (`index.html:3540`); lock P, no CSRF. Body `current_password` required in effect and untrimmed; `new_password` trimmed, at least 8 bytes and different from current. Outlet-flag sessions read `portal_outlet_users.pass` by session username, verify bcrypt, then update `pass`, nullable sealed `pass_view`, `pass_by=self`, `pass_at=NOW()`; missing row denies 403. Officer sessions reload `users.php`; missing current account denies 403; `$2y$` uses `password_verify`, legacy plaintext uses nonempty current plus `hash_equals`. `setPassword()` and `writeUsers()` update officer hash/metadata. Wrong/short/same password yields HTTP 200 `{ok:false,error}`; success `{ok:true}`. No transaction around the single outlet UPDATE or file write. Android: separate account stores and retain current-password proof.

### 9. `update_contact` — `auth.php:415-428`

Method `*`; browser POST (`orders.js:877`); lock P, no CSRF. Outlet session denied 403; officer must exist in current `users.php` or 403. Optional `email` and `mobile`; absent keys preserve values, empty keys clear them. `cleanContact()` lowercases/trims valid unique email and strips non-digits from mobile (removes leading `91` when 12 digits; accepts 8–13 digits). Invalid/duplicate returns HTTP 200 error. `applyContact()` and `writeUsers()` persist changes; success `{ok:true,email,mobile}`. No SQL. Android: enforce uniqueness against local officer accounts and keep outlet phone on the SAP master record.

### 10. `add_user` — `auth.php:429-505`

Method `*`; browser POST (`index.html:2591`, `orders.js:3765`); lock P, no CSRF. `actor(...,'super')`; HPCL super admin may create only HPCL `role=zone`. Required trimmed `username,password,role,label`; optional `filter,org,sheet_zone/sheet_zones,ros,hidden_cols`. Username ASCII letters/digits/underscore, role from six-role allowlist, exact duplicate check, password at least 8 bytes. `validateOrg()` requires a known portal zone for `rohan|hpcl`; organized users require chosen sheet zone(s). `cleanZones()` supplies regions and multi-zone fields. Initializes `level=zone` and `created_by=actor` for organized accounts; `setPassword()` adds hash/view/metadata; `writeUsers()` persists file. Success `{ok:true}`; validation errors HTTP 200; actor/storage errors 403/500. No SQL. **Unlike `add_super_admin` and import, this route checks only exact username duplicates**, so case-only collisions are possible. Android: keep that source distinction visible in compatibility tests and decide collision policy explicitly.

### 11. `add_regional_officer` — `auth.php:506-566`

Method `*`; browser POST (`orders.js:2482,3034`); lock P, no CSRF. `actor(...,'any')`: a Zone Officer is the parent; a super admin supplies `parent` naming an existing Zone Officer (HPCL super admin can choose only manageable HPCL parents). Required trimmed `username,password,label`, `ro` and nonempty valid `sales_areas`; optional `parent` for super admins. Success `{ok:true}`; validation HTTP 200, actor 403, storage 500. No SQL. Android: preserve parent and scope derivation.

### 12. `update_regional_officer` — `auth.php:567-613`

Method `*`; browser POST (`orders.js:2546`); lock P, no CSRF. `actor(...,'any')`; target must be a manageable Regional Officer. Body `username`, `ro`, `sales_areas` required in effect; optional `parent` (super admin only), `label,email,mobile,hidden_pages,new_username`. Parent move must name a Zone Officer and pass HPCL-super manageability; `cleanRegional()` checks allowed parent/actor regions. `cleanContact()` validates optional contact; `applyPages()` handles page visibility; move copies parent org/creator, then region-derived zone fields and sales areas replace old values. `renameUser()` may update MySQL references before the officer-file save. Success `{ok:true}`; errors HTTP 200 except actor/storage 403/500. No encompassing transaction. Android: update account and references atomically; retain parent/scoping checks.

### 13. `delete_user` — `auth.php:614-644`

Method `*`; browser POST (`index.html:2610`, `orders.js:3832`); lock P, no CSRF. `actor(...,'any')`; body trimmed `username` required. Self-deletion forbidden. Target must satisfy `canManage()`; `childrenOf()` blocks deletion of a Zone Officer with Regional Officer children. Removes only the officer entry from `users.php`; no SQL delete, no order-history cascade, no transaction. `{ok:true}` on success; input/not-found/children errors HTTP 200, actor/storage 403/500. ### 14. `add_super_admin` — `auth.php:645-691`

Method `*`; browser POST (`orders.js:3012`); lock P, no CSRF. Only `actor(...,'rsuper')` (non-HPCL super admin). Required trimmed `username,password,label,org` with `org=rohan|hpcl`; username ASCII letters/digits/underscore and case-insensitive uniqueness; password at least 8 bytes. ### 15. `update_super_admin` — `auth.php:692-711`

Method `*`; browser POST (`orders.js:2974`); lock P, no CSRF. `actor(...,'rsuper')`; body `username` required in effect, target must have `role=superadmin`; optional trimmed `label`, `hidden_pages`, `states`, `all_states`. Writes `users.php`, success `{ok:true}`, actor/storage 403/500. No SQL. Android: preserve self edit and state handling without conflating it with account geography.

### 16. `import_officers` — `auth.php:712-719`, `1417-1543`

Method `*`; browser POST in dry-run and save calls (`orders.js:2890-2900`); lock P, no CSRF. `actor(...,'super')`; body `rows` required nonempty array, max 600; optional `dry_run`, `org` (HPCL super forced to HPCL; otherwise `rohan` or default HPCL), `areas_by` (`region` or default sales area). Each row supplies `name,email,mobile,level,ro,sales_area,zones,states`; helper normalizes/truncates, validates known mapping, skips duplicate email, and creates Zone Officers before Regional Officers. Parent choice favors the most specific covering Zone Officer and a same-batch officer on tie. Username comes from email/name and avoids case-insensitive collisions. New accounts receive the import default password: one bcrypt hash and one sealed readable copy are reused within a batch; the response includes a per-row password on actual creation. Dry run writes nothing but still calls `passSeal()` and constructs in-memory accounts. One final `users.php` write occurs if any created; no SQL transaction. Returns `{ok,dry_run,org,counts,results[]}` with row `status`/`note`; empty/oversized arrays return HTTP 200 `{ok:false,error}`. Android: preserve row outcomes and dry-run semantics, but treat password disclosure as a security decision.

### 17. `convert_to_sales_areas` — `auth.php:720-728`, `1391-1415`

Method `*`; browser POST (`orders.js:2701`); lock P, no CSRF. `actor(...,'super')`; no business fields. HPCL super admin passes `canManage()` but current `superLimit()` returns null. Converted officers lose old district/sales-area fields; `users.php` is written only if at least one changed. SQL is read-only; no transaction across SQL read and file write. Returns `{ok:true,converted,how,left}`. Android: migrate legacy scopes idempotently without widening unmatched district-restricted officers.

### 18–23. Outlet profile routes — `auth.php:729-741`, `805-989`

An outlet, Regional Officer, or Rohan Zone Officer gets HTTP 403. `outletActor()` computes the actor's regions from the current officer file; super admins receive `regions=null` because `superLimit()` is not applied here. `ouEnsure()` may create `portal_outlet_users` on first use. SQL errors caught as `PDOException` by the route produce HTTP 500; ordinary validation errors are HTTP 200 `{ok:false,error}`. The outlet profile table is distinct from `portal_outlets` and has no declared foreign key to it.

## Helper dependency audit

There are **66 declared functions** in the four focus files: 47 in `auth.php`, 10 in `outlet-users.php`, 7 in `users-store.php`, and 2 in `regions.php`. All 66 bodies were reviewed. Direct callers below are source call sites; indirect callers are the route(s) reached by following those named callers. There is no general variable-function dispatch in these files; the one `$dbl(...)` call in `salesAreasFor()` invokes a local closure. A declaration-only textual search found no calls to `validateRos`, `superScopeFields`, or `genPassword` in supplied PHP; their reachability is **UNKNOWN**, because an external include/caller is not supplied. No helper is declared `UNUSED`. Unless noted, helpers read/write no SQL or file and return the stated pure value; PHP arrays are by value except parameters marked `&`. “Migrate” means preserve the behavior in a future local domain service; “adapter” means replace the server mechanism while preserving its visible contract. These are audited source contracts, not Android implementations.

## Account architecture, session fields and authorization

Officer accounts are keyed by username in a PHP-returned array in `users.php`, read and rewritten as a whole by `users-store.php`. The live file is missing. `03-demo-data/users.demo.php` and `03-demo-data/json/users.json` are demo fixtures only; the SQLite seed's `officer_accounts` table is a migration artifact, not an original portal table. The demo has ten officer records, including null-org and HPCL super admins, Rohan/HPCL Zone Officers and Regional Officers; it cannot establish live grants. Outlet profiles are separate `portal_outlet_users` rows keyed by SAP code, with bcrypt hash, optional encrypted view, editor/time and creator metadata. `portal_outlets` is the master SAP list; the profile has no schema foreign key to that table. `ouFind()` joins dynamically to obtain current `zone`, `ro`, `sales_area`, `state`, and `outlet_name`. Demo JSON supplies ten profile/master pairs. An installation's future SQLite officer and outlet stores must remain distinct, and all changes stay on that device.

The supplied `users.json` uses `pass_hash` rather than the PHP file's `pass` key; `build_demo_db.py:74-82` copies each account JSON into `officer_accounts.data_json` and stores that hash separately in `officer_accounts.pass_hash`. This is a migration representation, not a claim that `auth.php` can read JSON directly. `portal_outlet_users.json` has ten rows with `sap_code,label,pass,pass_view,pass_by,pass_at,created_by,created_at`; `portal_outlets.json` has ten master rows with zone/region/sales-area/state and contact/billing fields. The demo order/event JSON retains `created_by`, `decided_by`, and `username` references that explain why `renameUser()` updates historical SQL columns. Existing seed tests compare source JSON values and profile/master linkage; none run the PHP login against MySQL.

The officer session built at `auth.php:122-133` always has `username,role,label,filter,hidden_cols,hidden_pages,org,ros,level,sales_areas`; `org` may be null and arrays may be empty. It does **not** set `outlet` or `sap_code`. The outlet session at `outlet-users.php:76-93` has `username` equal to SAP, `role=zone`, profile `label`, `filter.zone` from the master, empty `hidden_cols`, `org=hpcl`, one `ros`, `level=regional`, `sales_areas` from master or empty, `outlet=true`, and `sap_code`; it does **not** set `hidden_pages`. The login and valid `check` responses include the current CSRF token outside the user object. `session_regenerate_id(true)` runs on both successful logins. `check` does not regenerate the ID; logout destroys the session. Officer `check` refreshes only six fields, as specified above, while outlet `check` reconstructs the entire outlet identity. Neither method proves Android persistence behavior.

`role`, `org` and `level` are separate: `userLevel()` returns regional only for an organized `role=zone` account explicitly marked regional; a legacy organized zone account defaults to Zone Officer. `created_by` defines parent-child management, not display labels. A super admin can edit account grants under route-specific restrictions; Rohan super admin is `role=superadmin` without `org=hpcl`, so a null-org super admin is considered Rohan. A Zone Officer may manage only Regional Officers they created. HPCL super admin manages HPCL `role=zone` accounts; the executable `superLimit()` returns null, so an older comment about limited management zones has no effect in this source. Regional Officers and outlet profiles cannot invoke the management routes because `actor('any')` rejects them. Organization changes of a Zone Officer propagate to children; loss of child regions or conversion away from zone role is rejected. The super-admin `states` field governs pending approval scope through `approvalStates()`, not account-list visibility. Source: `auth.php:990-1149,1268-1309`, `regions.php:175-201`.

The 18 `PAGE_IDS` at `auth.php:15` are `dashboard`, `rawdata`, `mis`, `entry`, `admin`, `neworder`, `myorders`, `approvals`, `allorders`, `returns`, `inventory`, `foc`, `sap`, `roreport`, `perms`, `zones`, `team`, `outlets`. `applyPages()` allowlists them and blocks self changes. `orders.js:216-244,291` hides tab buttons, and a hidden New Order page may still be opened to continue an edit. The server-side `actor()`, `canManage()`, outlet region predicate, `ordScope`, and other route guards enforce actions/data separately; `hidden_pages` is **not** an authorization grant or denial. The browser can show different account controls from the API, so Android must enforce permissions in domain operations, not only navigation.

The geographic mapping in `regions.php` has 16 sheet zones mapped onto 14 portal zones. `ORD_STATE_RO` maps states to regions, `ORD_RO_SA` maps regions to sales areas, and `ORD_SHEET_STATES` supports approval-state selection. Region names are matched to `portal_outlets.ro`; names and ordering are data, not derivable from labels. The mapping is shared by account and order scope and must be bundled locally as one versioned source. `cleanZones()` allows multiple sheet zones and an optional subset of their regions, deriving portal zones from the selected sheets. `cleanRegional()` requires one covered region and nonempty canonical sales areas. Historical accounts may use `sheet_zone`, `ros`, `zones`, `states`, districts, or null org and must retain their fallback semantics; do not flatten them into a single zone column.

## Password and session security findings

The original officer `pass` field contains a `$2y$` bcrypt hash for current accounts; login and own-password change also accept legacy plaintext, and successful legacy login rehashes it. New officer hashes use PHP's default `PASSWORD_BCRYPT` cost (the demo hashes show cost 10; the source does not hardcode cost for new officers). Outlet hashes use `ouHash()` with cost 8. The supplied hashes have been format checked by existing tests; **no password-verification compatibility test was run in this audit**. No hash or demo data was changed.

The portal intentionally keeps an additional recoverable password copy for non-super officer accounts and outlet profiles. `passSeal()` uses AES-256-GCM and a key derived from database credentials; `passView()` decrypts it only for authorized list views. `list_users` may return that plaintext to a managing super admin or the child's Zone Officer, never the owner and never for a super-admin target. `outlet_list` returns the decrypted view to every authorized outlet manager without a per-target `canViewPassword` check. `import_officers` returns newly generated credentials in its result rows. These are **existing source behaviors and sensitive-exposure risks**, not recommendations to replicate them without an explicit device security decision. The live `config.php` is missing, so its encryption key cannot be reconstructed; existing encrypted live `pass_view` values cannot be migrated using the demo configuration. Server-derived keys must never be bundled in the APK.

The source's CSRF protection is uneven: `auth.php` creates a token for each session, but officer mutation routes do not verify it; only outlet-profile routes enforce body CSRF. The JS `authPost()` sends `csrf` for those routes, while older `index.html` POST calls do not send it. `api.php` and `orders.php` have separate POST CSRF guards, which do not protect `auth.php` officer actions. HTTP method gating is also absent in `auth.php`. These are source security gaps to document and test, not permission to weaken the future offline service. `usersLock()` silently proceeds if the lock file cannot be opened, and `usersWrite()` falls back to in-place locked writing if temp rename fails. `renameUser()` commits SQL before the officer file is saved; `outlet_update` can change label before rejecting a short new password. A SQLite implementation can use local transactions for stronger atomicity, but any behavior change needs explicit parity tests and a migration decision.

## Source gaps and decisions before implementation

1. **Live `config.php` is absent.** `config.example.php` proves only the demo constant names and sample values. It cannot prove production DB credentials, password-view decryption key or any deployment overrides. The Android build must never contain live server credentials. Live encrypted `pass_view` migration needs an authorized secure export/decryption plan, or an explicit decision to omit those views.
2. **Live `users.php` is absent.** Source proves account shape and permission algorithms, not real usernames, grants, case collisions, legacy plaintext prevalence, hidden pages, scopes or creator hierarchy. Obtain a redacted field-level inventory and approved local data-migration material if production accounts must be carried forward. Demo users alone are sufficient for architecture tests, not for production identity migration.
3. **Security policy needs a product decision.** Decide whether readable password views, predictable outlet/import passwords, password return in import results, and session behavior on a local device are retained, modified, or removed. A change must be documented as a deliberate deviation from PHP, not silently presented as parity.
4. **Partial-refresh and atomicity behavior needs a parity decision.** Officer `check` leaves cached `role,label,filter`; rename commits DB references before a file write and omits database `pass_by` columns; outlet update can partially succeed. Determine whether Android should reproduce those defects or make local operations atomic and always refresh the full account. The source behavior above is verified; the Android policy is not.
5. **Three helper call sites are unknown.** No supplied PHP call to `validateRos`, `superScopeFields`, or `genPassword` was found. Do not mark them unused until any omitted include/customization is checked.
6. **Bcrypt compatibility is untested.** A future audit/implementation task must verify the supplied `$2y$` hashes against a PHP-compatible local verifier and negative inputs before choosing a device library. No such implementation was added here.

The unrelated missing `mis-data/seed.json` and `mis-data/template.xlsx` still block exact MIS parity, but do not alter the authentication rules audited here. The live files are needed for production account migration, not for documenting the supplied route logic.
