# API data entry, pending approval, notes and targets: source audit

## Executive summary and source files

All 19 `api.php` dispatch branches were inspected against `api.php:1-862`, their `index.html` callers, `mis-core.php`, `regions.php`, `users-store.php`, `auth.php`, `orders.php` order/MIS integration, `change-log.php`, `config.example.php`, `03-demo-data/schema.sql` and supplied JSON/SQLite seed. The 36 declared API functions are registered below. This is a static contract, not a working Android service or PHP/MySQL runtime parity test. Live `config.php`, `users.php`, the original `mis-data/seed.json`, the RO reference database and the `pending_entries` DDL/data are absent. Demo users and rows do not establish production grants or values.

The supplied JSON has 106 `portal_mis_rows`, one MIS meta row, 12 orders and 15 order items; its MIS fields include `src,item_id,gone,ver,notes`. The generated SQLite asset mirrors those seed values and has empty `audit_log` and `targets` tables, but no pending-entry table. These counts verify only the demo kit, not the live portal.

## Router-wide request and response contract

`api.php:42-85` decodes JSON from raw input (`null` becomes `[]`), chooses query `action` before body `action`, opens MySQL **before** starting the session and CSRF check, then dispatches by action. There is no HTTP method allowlist. The browser uses GET for reads and POST JSON via `index.html:1085` for writes. Any HTTP method PHP accepts can carry a JSON body; only POST checks `body.csrf` against `$_SESSION['csrf_token']` (403 `{error}`). Thus a JSON-body GET can reach writes without the POST CSRF guard. Unknown action is 400 `{error}`. Most action errors echo `{error}` with **HTTP 200**; `misFail` produces `{ok:false,error}` with an explicit code and exits. There is no router-wide exception handler. Uncaught SQL exceptions can expose server errors. The same-origin CORS check compares origin host with `HTTP_HOST`, not a general authentication guard.

`MIS_T=portal_mis_rows`, `MIS_META=portal_mis_meta`, `MIS_OUT=portal_outlets`, `PENDING_TABLE` comes from live config (demo example: `pending_entries`), `audit_log` and `targets` are API-created tables. `portal_orders`, `portal_order_items`, `portal_order_files` and `portal_products` feed MIS/order projections. `users.php` supplies current officer scope. A successful GET can write because `misEnsureSchema` seeds/changes schema and `misSync` creates/deletes order-derived MIS rows. Unless a contract below says otherwise, the PHP function performs no explicit transaction or row lock and has no idempotency token. Proposed Android operations use local SQLite only.

## Sales, import, pending state machine and actor matrix

The main record is a `portal_mis_rows` line with DATE `d`, nullable text and DECIMAL(12,2) EA / DECIMAL(14,2) litres, `src=sheet|order`, `gone`, `ver`, updater/time and optional `notes`. It has no creator-owner column. `sales` does not include pending entries; it includes approved order-derived lines only after `misSync`. The old `DB_TABLE`/`DB_COL_MAP` mapping and `resolveColumns` are no longer route-used. The browser import at `index.html:2292-2356` uses SheetJS `XLSX.read`, chooses `SALES_DATA` or the first sheet, finds the first row with a header containing “date”, and uses substring header matching for outlet, RO code, district, state, sales area, regional office, zone, item, EA and litres. It interprets slash dates as day/month/year, integer-parses EA and digits-only litres, defaults litres to EA×20 and item to HP DEF, and drops rows with no date or zero volume. The server never receives the file or checks its extension, header or byte size: `import` accepts JSON arrays only. Unlike `mis.php` import, this API has no 30,000-row limit. The browser updates its local display optimistically before the server confirms the import (`index.html:2350-2356`).

## Audit log, notes, targets and order integration

`audit_log` is on-demand (`id,action,username,details,created_at`); timestamps use MySQL `NOW()` under PHP's Asia/Kolkata default, subject to DB timezone. It records add/edit/delete/import, pending submit/approve/reject, notes and targets **after** their main operations. It does not record pending edit/delete, failed validation, old/new structured values or IP. Failed audit inserts are swallowed. No retention/update/delete route is present. This differs from `portal_order_events` and `portal_change_log`.

`notes` is one nullable text column on a MIS row; save overwrites/clears it, bumps revision and logs only a short note prefix. `targets` uses unique month/scope type/scope value with integer litres, no foreign key, no user ownership and no server format or nonnegative check. The frontend reads target rows for dashboard bars; `getSales` itself does not join targets. Historical target/note revisions are not retained.

`misSync` inserts approved nonhistorical order lines into MIS, deletes stale order-sourced rows, and preserves manually hidden (`gone=1`) order rows by `item_id`. `sales` LEFT JOINs order/item/file records for invoice/payment fields, calculates amount from paid EA (legacy fallback EA) and rate/GST, and separately returns a scoped pipeline summary. `portalOrderRows` is a legacy duplicate projection with no route caller; `portalOrderSummary` is live. A missing order table produces sheet-only sales and zero pipeline summary. The source does not automatically deduplicate an imported sheet row against its equivalent order row; imported history is excluded by the order creator marker only.

## Security findings and offline SQLite requirements

- GET-body writes bypass POST CSRF. `ro_lookup` and `get_targets` have no session check; `ro_lookup` can expose cross-zone outlets and reference DB errors. `pending_count` exposes a global count to any signed-in account.
- `add_pending` accepts any session and no field/geographic validation. `approve` has no row lock, status predicate on UPDATE, creator/state guard or duplicate MIS constraint; simultaneous approvals may insert two sale lines. `reject` logs success even when no pending row changed. `edit_pending`/`delete_pending` have a SELECT–write race and no audit.
- `save_note` can return success for nonexistent rows. `save_target` permits arbitrary/negative dimensions and litres after integer conversion. `audit_log.limit` has no bounds. `import` can accept unbounded arrays, exposes raw SQL errors and has no deduplication.
- Local SQLite must retain separate MIS rows, order-derived `item_id` unique link and `gone` semantics, revision metadata, pending entries, targets and API audit log. The seed already contains MIS/target/audit tables but **not** pending entries; schema design is a later authorized task. Index `pending(status,submitted_at)` and `pending(submitted_by,submitted_at)` would support reads; pending transitions, approval MIS insert/revision and audit should be one local transaction with stale-status checks. Preserve decimal representation and avoid floating-point financial drift. Actor scope must be checked at repository/service boundaries, including data returned to targets and reference views.
