# Orders, approvals, stock, delivery and returns: PHP source audit

## Scope and audit result

This report records the executable behavior of all **37** `orders.php` dispatch paths. It is a source contract for a future local SQLite implementation, not an Android implementation or a runtime parity claim. Source inspected: `orders.php` in full; the session/account dependencies in `auth.php`, `users-store.php`, `outlet-users.php`, `regions.php`; `change-log.php`; relevant `api.php` MIS/order references; `index.html`, `orders.js`, `salesorder.js`, `invoice.html`; `03-demo-data/schema.sql`, relevant JSON seed and the generated SQLite schema. Live `config.php` and `users.php` are absent. The demo account/outlet rows are not a live roster.

### Route-wide contract (applies to every entry below)

`orders.php:1049-1140` decodes JSON, substitutes an empty object for non-array JSON, merges nonempty `$_POST` ahead of the JSON body for multipart requests, and selects query `action` ahead of body `action`. There is **no global HTTP method allowlist**: each action accepts any method PHP can deliver. The browser uses GET for reads, POST JSON for writes, and POST multipart for file uploads. POST requests (including reads) require session CSRF in the body; GET requests do not. A JSON-body GET can therefore reach a mutating action without the CSRF check. The `public_invoice` branch runs **before authentication and CSRF**. All other branches call `ordUser()`, open MySQL, and call `ordEnsureSchema()` on every request; schema preparation can mutate tables even for a read. HPCL Super Admin is denied the actions absent from the explicit allowlist at `orders.php:1090-1094`. `ordFail()` emits `{ok:false,error}` with the specified HTTP code and exits; `ordOut()` emits `{ok:true,...}` and exits. Uncaught `Exception` rolls back an open transaction and becomes HTTP 500 `Something went wrong while processing the order. Please try again.`; non-`Exception` throwables are not covered by that catch. Field errors often add `fields` and HTTP 422. Successful read actions do not ordinarily begin transactions; exceptions and on-open legacy repairs are noted below.

Shorthand: **O/I/E/R/F/S/P/FOC/OUT/OL/CL/OU** means `portal_orders`, `portal_order_items`, `portal_order_events`, `portal_order_returns`, `portal_order_files`, `portal_settings`, `portal_products`, `portal_foc`, `portal_outlets`, `portal_outlet_log`, `portal_change_log`, `portal_outlet_users`. `U` means the separate `users.php` officer file. An action's source range includes its dispatcher line and implementation function. Unless stated, no file is changed, no transaction or row lock is used, and replaying a write has the stated overwrite/duplicate behavior rather than an idempotency key. All planned tests under `tests/regression/orders/` are **proposals**, not existing tests. Every Android target below means a device-local service over SQLite/app-private files, with no HTTP or cross-device synchronization.

## Cross-action rules and actor eligibility

`ordUser:532-592` reloads current U or joined outlet profile each request. An officer needs `role=superadmin` or organized `role=zone`; an ordinary officer needs a valid portal zone; Regional Officers with no assigned SA get 403. Outlet requires current profile/master linkage and a valid portal zone; `sap_code` fixes it to one SAP. `ordScope:602-637` is the read predicate: Rohan sees own/team non-drafts plus approved HPCL invoices in its zone/RO/SA; HPCL sees zone/RO/SA nonhistorical order subset plus own/team/outlet orders, with own SAP restriction; Rohan admin sees all or configured states plus own; HPCL admin excludes drafts except own, historical imports, and applies state scope. `hidden_pages` never enters these predicates.

## Stock, finance, delivery and offline requirements

Stock is **calculated**, not decremented: `ordStock:498-519` reads `stock_pid` total and subtracts SUM of I `ea` on O approved with `decided_at >= stock setting updated_at`; draft/pending/rejected do not consume. Unset stock is unlimited; disabled `cfg_stock_enabled` makes every item unlimited and usage zero, while preserving values. Approval serializes on existing `stock_%` S rows and the O row, then recomputes stock. If no stock rows exist, the stock-row lock has nothing to lock. `set_stock` may reset a baseline when a changed value is saved; the UI's unchanged available value is skipped. Validate stock at save/submit and again at approval. FOC is selected at the greatest `min_qty <= paid EA`; `ea=paid+foc`, `vol=ea*20`, and stock/MIS count total EA while billed amount uses `paid` (legacy `paid=null` lines bill `ea`). `ordFocMigrate` can change legacy rules on first schema ensure; the bundled seed already has `foc_list_v1` and must not rerun it.

Approval creates `RCSO2/<April–March FY>/<n>` voucher; eligible tax invoices get `RETI/<FY>/<n>`. `ordGiveNumber` takes max numeric suffix +1 and catches unique conflicts up to five attempts; it does not verify an UPDATE affected a row before returning. `ordFinalizeSO` fills only missing rate/GST from current prices. Manual invoice mode suppresses generated invoice number. A Rohan SO approved now sets `inv_flag=1` and random `doc_token`; older SO/historical rows can remain without it. A generated invoice can be corrected in O `invoice_edits` without changing I, number or status. Uploaded invoices are F records and cannot be edited through `edit_invoice`.

File bytes live under server `pod-files`, with a random basename; F stores original name, MIME, size, uploader/time. The PHP route validates extension and leading bytes but does not fully parse the document. POD requires payment first and completes delivery; receipt is replaceable until delivery; manual invoice replacement stops at delivery, though the first upload is allowed then. SQL rollback cannot undo a file move before commit, so upload failure/crash can leave orphan bytes; successful replacement deletes the old bytes after commit. Android needs app-private files, persistent SQLite metadata, staged file replacement and a recovery scan. No network upload/download is part of the migration.

Returns stay in R with pending→approved/rejected; a rejected latest request permits another pending request. The order remains approved/delivered, and return approval does **not** alter stock, invoice or MIS. `ordRetMayDecide` uses configurable organization × level flags, `ordScope` and state limits apply, and nonadmins cannot decide their own request. A super admin may decide its own. File/document and return mutations should use explicit local transactions and regression tests for crashes/concurrent taps.

The QR currently embeds an absolute server URL `invoice.html?t=<doc_token>`, and that page performs an unauthenticated HTTP fetch. The token is a bearer secret; a copied QR can reveal the redacted invoice fields to anyone with server access. An offline app requires a product/security decision on QR payload, signature/integrity, privacy, cross-installation readability and revocation. Do not choose a format or embed a server URL during this audit.

## Security findings and unresolved decisions

- Global POST CSRF applies after authentication; GET-body mutations are accepted without CSRF. Public invoice is unauthenticated. A local domain service still needs explicit actor checks for every operation.
- `ordGet` can mutate legacy rows and assign numbers on GET. `ordEnsureSchema` runs on every route and may write. Android should use explicit migration stages; parity tests must record any changed timing.
- `ordSapSave` SAP rename moves history but not outlet profiles or old order SAP references. `sap_import remove` deletes master outlets and profiles but leaves order snapshots. Decide reference/session behavior before implementation.
- `ordSapImport` SQL error text is returned to the browser. `change_log area=mis` uses `chgFetch` without a specific MIS authorization guard in this route. `set_prices`, `set_stock`, `set_perms`, `delete_product` have multiwrite partial-failure exposure.
- Approval locks existing stock setting rows, but a disabled/unset stock setting has no lock row; validate the exact concurrent behavior on a live MySQL copy if parity is needed. Return request locks the latest existing R row, but the first request has no row to lock; no unique pending-return constraint is declared.
- `seen_updated_at` is optional on approval/rejection; an omitted value skips stale-edit detection. Invoice edits do not use it. File upload bytes and SQL metadata are not one atomic resource.
- Live `config.php`/`users.php` and production DB are unavailable. The demo email/designation mapping in `ORD_HPCL_DESIG` is expressly demo-only. Production officer grants, outlet completeness, legacy order shapes, true stock contention and original QR usage cannot be confirmed from this kit. The missing MIS workbook/seed still affect later modules, not these route contracts.
